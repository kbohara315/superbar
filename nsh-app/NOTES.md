# Superbar on nsh: working notes

Replacement for the GNOME extension (../extension) and Zig CLI (../src), written in TSX on nsh.
Those stay untouched; this app lives alongside them. Source of truth for behaviour: ../docs/usage.md and ../docs/cli.md.

## Toolchain (already installed)
- `export PATH=$HOME/.nsh/source/target/release:$PATH` (nsh `0.4.0 (0e4a20b)` built from the pinned source, which has `Tray` in `nsh/desktop`). The released CLI at `~/.nsh/bin/nsh` (`0.4.0 (e626a8d)`) has the same version string but a different commit: it lacks `Tray` and rejects `notifications` in nsh.json, so its `test`/`check` fail for this app. `rust_app::Nsh::of` checks the version string, not the commit, so use the source build.
- Tests (headless, no display): `nsh test`  | typecheck: `nsh check` | run: `nsh run App.tsx` (needs the desktop session).
- Docs of record: ~/.nsh/source/website/docs/*.md and website/modules/*.md (nsh-desktop.md, standard-modules.md, globals.md).

## Platform facts
- Capabilities live in nsh.json. Allowed keys: network, webview, statusBar, clipboard, picker, speech, openUrl, process, fs, host. `notifications: true` IS a valid capability key on nsh main (it was rejected by the released 0.4.0); it is required for alerts.
- fs roots: `${homeDir}`, `${dataDir}`. Read: ~/.codex, ~/.claude, /proc, /sys. Write: ${dataDir}.
- `Notifications` is imported from "nsh" (requestPermission(), show({id,title,body})).
- Tray: `Tray.set({icon, tooltip, menu, onClick})` from "nsh/desktop"; TSX only; follows signals inside an effect. Icon is an SVG/image src. This GNOME has the AppIndicator extension.
- Second window: `Window.open(Component, {id,title,size,frame})` (Linux/Windows). Returned window has focus()/hide()/close().
- `fetch`, `fs/promises`, `process` (run/spawn/env/platform) behave like Node/WHATWG; see standard-modules.md.
- Shared types: src/types.ts (do not change without the coordinator).

## Lifecycle and asset facts (from T4)
- The app is tray-resident. Linux has no API to hide the main window completely: it is minimized at startup (can reappear via Alt+Tab). The dashboard is `Window.open(..., {id:"dashboard"})`; nsh has no close interception, so closing it by the user unmounts it and the next open starts on the usage screen. Closing the MAIN window ends the app wherever the main window is what gets closed (see "Closing the main window" below for what nsh documents per platform; Linux packaged behaviour is unverified). Hide uses `hide()` on the second window and `minimize()` on the main one (both, if both are showing).
- SVG/asset imports must sit under the entry's directory (`../` imports 404 in the dev server): use `src/ui/assets/` imported from `App.tsx`.
- The tray icon is a square 24x24 gauge per provider (panel icons can't carry text), with three shapes so the state reads without colour: a ring with its amount as the arc; a solid filled DISC in the alert red when either window is at 90% used (the only filled shape); a solid grey RING when there is no 5-hour value (never dimmed). The glanceable text is in the MENU: its first lines are disabled (pill line with window and ` wk!` / ` !` / `(stale)`, metrics line, status line). On GNOME the AppIndicator extension does not show the SNI tooltip, and a click opens the menu; the tooltip carries the same strings for panels that do show it.
- Tray updates: the tray is re-sent only when its icon, tooltip or menu content changed (installTray compares the payload).
- Tray Title: nsh's Tray takes no title and the Linux dev host hard-codes `"nsh"` (`nsh-linux-host/src/lib.rs`); `nsh run --name` is rejected on Linux. A packaged build takes its title from `nsh.json`'s name (`nsh-linux-app` reads `app.json`). So a dev run's tray Title stays `nsh`.
- Tray clicks: nsh's `AppWindow` reports neither focus nor visibility, so a tray click always raises the dashboard; hiding is the menu's "Hide dashboard". The controller's schedule runs on `performance.now()` (monotonic); wall-clock is for display only.
- Capabilities (nsh.json): fs read ${homeDir}/.codex, ${homeDir}/.claude, /proc, /sys, ${dataDir}; write ${dataDir}; process.execute chmod, df (Linux/macOS), top, vm_stat, sysctl, netstat, pmset, ps (macOS); process.env CODEX_HOME; network chatgpt.com, api.anthropic.com. No Windows executable is granted: Windows metrics are the app's own Rust module (see "Windows metrics" below). `"rust": "native"` makes the app mixed (TSX + the crate in native/).
- Known limits: CODEX_HOME only works inside ~/.codex (fs roots are static). Headless `nsh test` denies native fs/process (use injected fakes; real-host checks need `nsh run` or `nsh test --target linux`).
- Screenshots via the XDG portal write ~/Pictures/Screenshot.png: check it does not already exist before taking one.
- Async work (controller.ts ASYNC AUDIT): every external call goes through `bounded(token, task, ms)` (never invoked for a stale generation; timeout and stop() settle it); queued metric/process-list runs check their gate before each invocation; all timers are token-guarded and cancelled by stop(). Settings are written by the store's queue (see below), not by the controller's generation: a stop never cancels a write, and the store's queue outlives stop()/start().

## Settings file (store.ts)
- One file: `${dataDir}/settings.json`. A save writes `settings.json.<id>.tmp`, chmods it 0600 and checks it, then renames it over settings.json. The folder is 0700 (made so on save, required on read; POSIX only, windows skips the modes).
- Ordering: every read and write of the folder goes through one serial queue at module level. A write is issued only after the previous underlying write has settled. Writes waiting in the queue are coalesced (only the newest is written next). A read waits behind the writes requested before it.
- A write that never settles holds the queue. The controller then shows "Not saved: the settings write is still running..." after SAVE_TIMEOUT_MS, without issuing a second write; the note clears when the newest save lands.
- One way in (controller.ts applySettings): every change of the settings, a user's edit, the first load and a late read, is published by `applySettings(next)`, which runs the runtime transitions (provider timer, alert permission, each metric's sampler and timer, system refresh) by diffing previous and next, and then applies the persistence rule. There is no second path. Only a started generation runs transitions.
- Re-entrancy (controller.ts applySettings): applications run one at a time. A change requested while one runs (a transition's callback changing the settings, such as a sampler's read or a permission answer) is queued as `pendingApply` and applied next; the save reads the current settings, and a superseded application does not save. Each transition step checks that its generation is still running, so a stop inside a callback runs no further sampler, timer or permission work.
- Queue bookkeeping (store.ts): edits queued behind a waiting write share its one completion promise, so the controller watches each save promise once and holds one stall timer per write, however many edits arrive.
- Persistence rule (saveIfNotOnDisk): once a read has settled (`baseKnown`), the applied settings are written whenever they differ from `lastWritten`, the text the disk is believed to hold (handed to the store, or said by the last read). A no-op reconcile writes nothing. A failed save clears `lastWritten`, so the next change or read writes again. Before a read settles nothing is written.
- Reconciliation (applyRead): the read's answer is the base (for a missing, damaged or untrusted file, the defaults); the overlay of changes made since the read was requested is laid over it. If a write was handed out after the read was requested, the queue runs it after the read, so the disk ends with that text and no second write is made. A read that is superseded, or whose generation was stopped, changes nothing; the next start reads again.
- Limit: a known failed save is not kept across a restart: the file is the truth, and the read reverts the displayed value to it (the file's value is shown and saved, not the failed one).
- Notes: the loading note (`Settings are still loading from disk…`) is shown while a read is pending and clears when it settles; the unusable-file note clears when a save lands; the write note clears when the newest save lands.
- Reads never follow symlinks and never throw: a symlink, a directory, a group/other-readable file, a file over 64 KiB, or a folder that is not 0700 is `untrusted` and gives the defaults with a note. Damaged JSON gives the defaults with a note. A missing file gives the defaults with no note.
- Temp files: on read, `settings.json.<hex-and-dashes>.tmp` regular files older than 10 minutes are removed. Only names matching that pattern exactly, and only as listed in the folder.
- Interim `settings.<digits>.json` files from earlier builds are not read, migrated or removed. The legacy `settings.json` is the file itself.
- Limitation (documented, not solved): one Superbar instance is expected. Two instances writing the same folder: the last writer wins, and every write is an atomic rename, so the file is always one whole valid version.
- The `version: 1` field in settings.json is the settings schema marker, not a save number.

## Windows and macOS (code paths written from nsh's docs and source; NOT run on a Windows or macOS host)
nsh facts used (website/modules/standard-modules.md, nsh-desktop.md, crates/nsh-core/src/access.rs, element/system.rs):
- `process.platform` / `os.platform()` are Rust's names: `"linux"`, `"windows"`, `"macos"` (never Node's `win32`/`darwin`). Anything but `"windows"` is treated as POSIX here.
- `os.homedir()` is the host's configured home, the anchor of `${homeDir}` in nsh.json. `process.env` holds only granted names (CODEX_HOME), so HOME/USERPROFILE are normally absent: `homeDirectory()` (providers.ts) asks `os.homedir()` first, then HOME, then USERPROFILE.
- The sandbox compares paths by component after canonicalizing, so `\` and `/` and case do not fool it on Windows, but a verbatim `\\?\` anchor (which nsh's code anticipates for `${dataDir}`) has no `/` separator: every path under the data folder is built by `childPath()` (providers.ts; also used by store.ts), which extends a backslash folder with `\`. POSIX output is unchanged (`dir/name`).
- Env names match case-blind on Windows only; `credentialLocation` does the same for CODEX_HOME there.
- Windows file errors: nsh reports PermissionDenied as `EACCES` (no errno table off Unix).
- `Window.open` runs on Linux and Windows and THROWS elsewhere (macOS). `Tray` is documented for all three desktops, as are `Window.orderFront/minimize/setFrame`. `Window.setSkipTaskbar` only does something on Windows (nsh's Linux and macOS platforms match `SetSkipTaskbar` to a no-op). `windowState()` is documented for macOS only ("macOS reports the window's state"; only nsh-platform-macos implements it): on Windows and Linux it can be null, and the app falls back to its own shown flag.

Credentials (providers.ts `credentialLocation(codex, {env, homeDir, platform})`): Windows drive paths (`C:\Users\me`, `C:/...`, `\\?\C:\...`, UNC shares) parse; `~/.codex/auth.json` and `~/.claude/.credentials.json` are built with the platform's separator; CODEX_HOME must be inside `~/.codex` (case-blind on Windows, exact on Linux/macOS, `..` refused) or it is refused with the existing message. Without `platform` the POSIX rules apply (old behaviour).

Settings and snapshot persistence:
- Windows has no POSIX modes: neither store requires or sets 0700/0600 there (nsh grants no way to read or set ACLs; protection rests on the per-user data directory, not checked). macOS and Linux enforce modes through the granted `chmod` (a bare name; macOS GUI PATH includes /bin).
- store.ts retries a rename that Windows refuses (EPERM/EACCES/EBUSY, target open elsewhere) 4 times (25/50/100/200 ms), Windows only; other errors and POSIX are not retried.
- providers.ts lock: renaming a staging directory onto an existing lock fails with EEXIST/ENOTEMPTY on POSIX but EACCES on Windows. There (only) EACCES/EPERM/EBUSY now means "a lock is there" if one is found, so a live lock is `busy` and a stale one is broken; the error is rethrown if no lock exists.

Startup, dashboard and tray (App.tsx):
- Linux/Windows: the dashboard is a second window (`Window.open`). If `Window.open` throws, or on macOS (where it always does), the MAIN window shows the dashboard: a tray click calls `Window.orderFront()`, "Hide dashboard" minimizes, and, where the host reports it (macOS), `windowState()` (minimized/hidden) drives the menu's Hide item; elsewhere the app's own shown flag does. The window is sized to the dashboard (`setFrame`) and starts minimized.
- Windows taskbar rule (src/windows.ts): the main window leaves the taskbar (`setSkipTaskbar(true)`, nsh's `ITaskbarList::DeleteTab`) only while it is a hidden placeholder, i.e. a second window carries the dashboard and the tray is up. When the main window has to carry the dashboard (tray failed, or `Window.open` threw), `showMain` clears the flag before `orderFront`, and "Hide dashboard" then only minimizes it, leaving the taskbar entry so the user can bring it back. The second dashboard window has its own taskbar button (nsh's windows.md); this app does not hide it. nsh's source says the taskbar forgets a deleted tab when a window is shown again, so nsh re-applies the choice on show; what an `orderFront` restore of a minimized window does with the flag still set was not checked, which is why the flag is cleared first. Not run on Windows.
- If `Tray.set` throws, the main window is NOT minimized (or is restored) and carries the dashboard, so the app is not unreachable. A second dashboard window showing at that moment is hidden first (`retireSecond`), so one Hide and `shown()` cover what is on screen; if that hide throws, the second window stays tracked as showing and each Hide retries it. The main window's and the second window's visibility are tracked separately (`mainShown`, `secondShown`); `shown()` is either. The same hide-then-raise applies when `Window.open` throws on a re-open while a second window is up.
- `onTrayFailed` raises the main window until one raise succeeds: installTray re-sends changed payloads and each attempt may fail again, but once `orderFront` has worked later failures do nothing. A failure whose `orderFront` threw is not latched, so the next failed `set` retries. `trayFailed()` (sticky, set on the first failure) is what startup uses to leave the main window up. A tray that is accepted but invisible (GNOME without AppIndicator) cannot be detected from the API.
- Wiring (App.tsx): `startTray` (src/windows.ts) installs the tray through `reportingTrayFailure` (a wrapper that tells the windows about a failed `set`, then rethrows) and only then calls `hideMainWindow()`. The real `nsh/desktop` calls and `process.platform` in App.tsx are still not injectable; the install-then-hide order and the failure reporting are tested through `startTray` with the real `installTray` over a fake tray port.
- The shown flags are set only when `orderFront` / `Window.open` did not throw (and cleared by Hide only when `minimize`/`hide` did not throw).
- Closing the main window: nsh's macOS doc says closing the window (or Quit) stops the engine and returns from `run_app`; its Windows doc says closing the main window closes the other windows and ends the app; its Linux doc says closing the window ends `nsh run`. What a closed main window does to a packaged Linux app, or one a tray keeps alive, was not verified (nsh's source, `nsh-platform-linux/src/app.rs`, closes the main window by stopping its engine; an earlier note that "the tray keeps a Linux app running" came from a GNOME run only and is not documented). Nothing in the TSX API intercepts the close (`keep_alive_on_close`, which retains the macOS window and engine, is a Rust `AppOptions` field with no `nsh.json` or TSX switch). So it applies wherever the main window is the dashboard: on macOS always (its close button and Cmd+W quit the app, a Dock/window app rather than menu-bar-only until nsh exposes that option), and on Linux and Windows after a tray failure or a `Window.open` fallback; closing the hidden placeholder on Linux/Windows ends the app too. Unavoidable from this app.
- Windows placeholder risk (unverified): the placeholder is hidden by `setSkipTaskbar(true)` (`ITaskbarList::DeleteTab`) then `minimize()` (`ShowWindow(SW_MINIMIZE)`, `nsh-platform-windows/src/chrome.rs`). nsh documents no command that hides the main window, and Windows may show a minimized window without a taskbar button as a small caption strip near the screen edge. This was not seen or ruled out (no Windows host). No undocumented workaround (off-screen frame, zero size) is used. If the strip shows up on a real Windows host, the options are to keep the taskbar entry (drop `setSkipTaskbar(true)`) or to ask nsh for a hide-main-window command.
- Tray icon colours: nsh's docs say an SVG tray icon "is a template drawn in the color of the menu bar's or taskbar's text" on macOS and Windows, and nsh's source (`desktop/menu_icon.rs`, `nsh-platform-windows/src/tray.rs`) says "only its alpha counts". So on macOS and Windows the provider colours and the alert red are expected to be lost; the shapes (ring, arc, solid disc) and the opacities survive because alpha is kept, so the state still reads from shape, but "red when high" holds on Linux only. A bitmap keeps its own colours for menu icons per the same source; whether that holds for the tray was not checked. The icon builder is in tray.ts and was not changed here.

Not done / blocked (needs nsh.json or packaging, outside this change):
- macOS: Claude Code keeps its login in the Keychain, not in `~/.claude/.credentials.json`, so Claude shows credentials_missing on macOS until a `security` execute grant (absolute path) and a Keychain reader exist. Codex's file path works if `cli_auth_credentials_store` is file. macOS commands are matched by exact string; bare `chmod`/`df` resolve through PATH.
- nsh.json fs roots `${homeDir}/.codex` and `.claude` serve Windows and macOS unchanged (`${homeDir}` is native), but `/proc` and `/sys` are Linux-only grants (metrics).
- No Windows/macOS host here: nothing above was run on one. Tests use fakes with those platform names (src/providers.platform.test.ts, src/store.platform.test.ts). The window logic is in src/windows.ts behind a `DesktopPort` and tested in App.test.tsx with a fake desktop (tray failure with and without a second window, retry after a throwing `orderFront`, `Window.open` fallback with the Windows taskbar flag, reopen, hide, shown-flag paths, and `startTray` order and failure reporting). App.tsx's own wiring (the real `nsh/desktop` calls and `process.platform`) has no automated test: it cannot be injected into a headless `open("./App.tsx")`. Verified with `~/.nsh/source/target/release/nsh` (0e4a20b) only.

## Windows metrics: an in-process Rust module (native/, src/winmetrics.ts, src/metrics.ts)
No PowerShell, cmd, wmic or any other program or script: nothing on Windows starts a process, and `nsh.json` grants no Windows executable (a test checks that no interpreter name is granted and that a Windows sampler starts no command). An earlier version collated one PowerShell script per sample; it and its `powershell` grant are gone, and so are its parsers, cadence floor and residual-risk discussion.

How the mixed app is built (checked against ~/.nsh/source docs: website/docs/rust.md, docs/dev/tooling.md "Apps with Rust components of their own", examples/rust-exports):
- `nsh.json` `"rust": "native"` names the crate `native/` (package `superbar-native`, `#[native_module("superbar/native")]` in native/src/lib.rs). TSX imports it as `import { WindowsMetrics } from "superbar/native"` (only src/winmetrics.ts does). Its TypeScript declarations are generated from the Rust doc comments into `.nsh/types/superbar/native.d.ts` by `nsh check`/`test`/`build`/`run`.
- nsh writes a Cargo workspace in `.nsh/rust` and builds the describe program, the headless test runner (`nsh test` runs `cargo test` in native/ first) and the platform hosts/runners with the crate linked in. TSX edits stay hot; Rust edits restart `nsh run`. The first build compiles nsh-core/nsh-base (about 2.5 min here); later ones are seconds.
- Dependencies: native/Cargo.toml takes `nsh-core` and `nsh-base` from the public repository, as Git dependencies pinned to one exact commit (`git = "https://github.com/longbridge/nsh"`, `rev = "0e4a20bd41ee72a35515cecbf9a7fba88742d911"`), with no local path. `nsh` (`rust_app::Nsh::of`) requires all app nsh crates to come from one source; for Git sources it compares the checkout's version string to the running `nsh`, not the commit. A version mismatch silently retargets to the same crates.io version rather than rejecting clearly. The released CLI and pinned source both say 0.4.0, but only the pinned commit has the required `Tray` API, so use the source build from that commit and change both dependency `rev`s together. The first build needs network access to github.com and crates.io; native/Cargo.lock pins the same commit. With a released nsh that has `Tray`, use `version = "=<that version>"` for both. `windows-sys` 0.61 is a `cfg(windows)` dependency only (nothing compiled or linked elsewhere); building on Linux fetched its source from crates.io once for the lockfile (`cargo fetch`).
- Generated runners: `.nsh/rust/{linux,windows,macos}-{host,app}/main.rs` are generated from the stock platform hosts plus `set_ui_sets(vec![nsh_base::registry(), <our set>])`. This keeps the same platform crate integration for Tray and Window; the Linux package built successfully, while Windows/macOS runners have not been built or run here.
- Not sandboxed: nsh.json capabilities govern the TSX/JS the engine runs. Rust in the app's own crate is native code in the app process, outside that sandbox (nsh has no capability to gate an app's own Rust module). The control is the API's shape: `WindowsMetrics` has eight zero-argument functions that return numbers (`supported`, `cpuTimes`, `memory`, `swap`, `disk`, `networkInterfaces`, `battery`, `processes`), takes no path, command, URL or script, writes nothing, and the crate has no dependency besides nsh-core/nsh-base and `windows-sys`.

The Rust API (native/src/metrics.rs; Win32 calls in native/src/platform/windows.rs; the pure conversions, tested on any OS, in native/src/decode.rs):
| function | Win32 | returns |
|---|---|---|
| `cpuTimes()` | GetSystemTimes | idle/kernel/user, 100 ns ticks since boot (kernel includes idle) |
| `memory()` | GlobalMemoryStatusEx | physical total/available bytes |
| `swap()` | EnumPageFilesW + GetPerformanceInfo (page size) | page files total/used bytes; no page file is 0/0 |
| `disk()` | GetSystemWindowsDirectoryW + GetDiskFreeSpaceExW | system volume total / free-to-caller bytes |
| `networkInterfaces()` | GetIfTable2 (FreeMibTable) | physical (HardwareInterface), operationally Up, non-loopback, non-tunnel adapters: index, name (Alias), rx/tx bytes |
| `battery()` | GetSystemPowerStatus | percent, charging, acPower, secondsLeft; null without a system battery or with an unknown percentage |
| `processes()` | CreateToolhelp32Snapshot + OpenProcess(QUERY_LIMITED_INFORMATION) + GetProcessTimes + GetProcessMemoryInfo, GetActiveProcessorCount | cores and per process pid, start time, exe name, CPU ticks, working set |
Off Windows every function returns null (the stub, native/src/platform/unsupported.rs); `supported()` says which.

TSX side (src/metrics.ts `MetricsSampler`, constructor's 6th argument is the injectable `WindowsSource`, default the Rust module): the module returns counters and the sampler does what Linux does with /proc: a CPU baseline (first reading is "sampling…", then 1 - Δidle/Δ(kernel+user)), network rates from counter deltas over `now()` between reads (adapters keyed by interface index; only adapters in both reads count; a reset counts as zero), memory = total - available, disk with the shared free-space trend, process lists (CPU share = Δprocess ticks / Δmachine ticks like Linux's jiffies, keyed by pid+start time so a reused pid is a new process; first reading shows rows as "—"; memory list = working set, ".exe" stripped). Calls are synchronous and in-process, so the old 2 s Windows cadence floor is gone: every metric follows its own interval (a 1 s network tile really samples every second). Unavailable honestly: a failed call, a non-number, or a throw makes that metric "unavailable"; no estimate.
- Temperature stays unavailable on Windows (no unprivileged documented source that is a CPU/GPU temperature).
- Battery: status is "Charging" (Windows charging flag), "Full" (on AC at 100%), "Not charging" (on AC, below 100%, not charging), "Discharging" (off AC) or empty when Windows does not say. Time left shows only while discharging and when Windows knows it (BatteryLifeTime, not the 0xFFFFFFFF sentinel, at most 99 h). Windows reports no time to full, so a charging battery shows none; that is "unknown", not a guess.
- Process lists only include processes the user may open with PROCESS_QUERY_LIMITED_INFORMATION; protected/system processes that refuse are left out, not shown with made-up numbers. pid 0 (System Idle Process) is not listed. The snapshot runs on the UI thread (a few ms for a few hundred processes, expected; not measured) and only while a CPU/memory list is open.

Tests: native/ has `cargo test` unit tests (decode.rs: FILETIME join, UTF-16 names, adapter selection, battery decoding, pages to bytes; the stub), run by `nsh test` before the TSX tests. src/metrics.test.ts has a `FakeWindows` (a typed fake of the module) for every Windows sampler, plus: the real module returns null everywhere off Windows (so the generated binding is exercised), no command is started by a Windows sampler, no interpreter is granted, `manifest.rust === "native"`. On a Windows host the same file checks the real module's answers for shape (`nsh test --target windows`).

Cross-target checks from Linux: `cargo check --locked --target x86_64-pc-windows-gnu` passes after installing the Rust target and MinGW-w64 compiler; this type-checks the Windows FFI but is not a Windows runtime test. `cargo check --target aarch64-apple-darwin` could not complete here because Linux `cc` is not Apple's compiler and the Apple SDK is absent. `nsh package --target windows` must be run on Windows with nsh 0.4.0: its Windows platform currently uses the host target triple, so invoking it on Linux produced an ELF binary named `Superbar.exe`, not a usable Windows app.
